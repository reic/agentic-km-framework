你正在執行 personal-km 的「**上架待確認**」程序——也就是使用者說「確認」**之前**那一步。動手前先讀 `personal-km/PERSONAL-KM.md` 規範（§C gate、卡片精瘦原則）。

**目標卡**：`$ARGUMENTS`
- 有指定 slug → 處理該卡。
- 留空 → 掃描 `personal-km/1-tuning/`，找出「## 我的觀點 ★（傳說食材）」**已是使用者真實立場/判斷**（不是 AI 留的引導提問）、且尚未在 `2-cards/` 或待確認清單中的卡，列出來讓使用者挑。

對每張目標卡依序做：

1. **Gate 檢查（硬條件）**：打開卡，確認「## 我的觀點 ★（傳說食材）」**非空、且是使用者的觀點**（不是編號提問這類空殼）。仍是空殼 → **不上架**，回報「觀點層未填，請先補」。

2. **定稿前 metadata 健檢**（**只提案／順修 metadata，絕不改動觀點層任何一個字**）：
   - `type`：若已是使用者原創判斷主導，建議由 `消化` 改 `觀點`／`經驗`／`提問`（撈料時 type∈{觀點,經驗,提問} 才會被優先撈到）。
   - `related`：與內文「## 連結」比對，補齊漏掉的關聯卡。
   - `tags`：至少有領域標籤（裸字、**不加 #**）。
   - `source`／`trigger`：確認存在；來源若是已刪 inbox 原檔，`source` 用文字描述、**不要留死連結**。
   - frontmatter 內 `[[連結]]` 一律加引號 `["[[X]]"]`。**不要**加 `density`／`updated`（已廢欄）。

3. **上架**：在 `personal-km/_pending-confirm.md` 的「## ☐ 待確認」區追加一行
   `- [ ] [[卡slug]] — 一句重點`
   （已在清單則不重複；若該區現為「（目前無待確認項）」先清掉再加）。

4. **回報**：列出上架了哪些卡、各自建議的 metadata 修正，並提醒下一步：**在 Obsidian 把該行打勾 `- [x]` → 說「確認」**。

**界線**：本步**絕不**把卡移進 `2-cards/`、不寫 log、不動密度——那些是「確認」動作的事。**觀點永遠使用者拍板，AI 不代筆觀點。**
